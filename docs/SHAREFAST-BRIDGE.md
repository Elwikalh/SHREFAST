# ربط الحبوب بشير فاست — مرحلة تجهيز فقط

> **Draft / لا تفعّل في الإنتاج.** هذه المرحلة تجهز النقل ولا تستبدل سوبر إكس. لا يوجد حذف للقديم، ترحيل بيانات، نشر تلقائي، أو تحويل تشغيل. الإعداد الافتراضي في الحبوب هو القديم، وفي شير فاست الاتصال مغلق.

## نطاق التغيير

- عقد إصدار 1 مطابق في الريبوين وتوقيع HMAC على الوقت والطريقة والمسار والاستعلام والجسم، بمهلة 5 دقائق، وحد جسم 16KB.
- هوية الحبوب تؤخذ من إعداد السيرفر، وليس من جسم الطلب أو رابط شاشة. لا تستخدم GitHub PAT كسر تشغيل ولا ترسله في الشات.
- إنشاء مهمة واحدة لكل UUID طلب مطعم، مع fingerprint ثابت. تكرار الإرسال يعيد نفس المرجع؛ تغيير البيانات تحت نفس UUID ينتج conflict للمراجعة.
- إلغاء آمن قبل بدء الرحلة. الإلغاء يسجل tombstone حتى قبل الإنشاء، لمنع ظهور توصيلة متأخرة بعد timeout. بعد بدء الرحلة يحتاج تدخل مشغّل، ولا يتم تجاوز الحالة بالقوة.
- إنشاء الطلب وربطه في شير فاست داخل معاملة واحدة. لا تعديل لواجهات التاجر العامة أو جلسات الدخول أو صلاحياتها.
- جدول إرسال دائم في الحبوب داخل معاملة حفظ الطلب، مع lease وإعادة محاولة وbackoff؛ لا HTTP أثناء حفظ طلب الأكل.
- بناءً على قرار المالك، الإرسال لا ينتظر تأكيد إنستاباي. حقيقة الدفع مستقلة؛ الرد من التوصيل لا يؤكد دفع المطعم ولا يغلق طلب الأكل.
- polling يحفظ مرجع المندوب والحالة في جدول الربط فقط. **عرض هذه البيانات داخل الشاشات لم ينفذ بعد** في هذه المرحلة.

## إعدادات اختبار منفصل فقط

نماذج بلا أسرار موجودة في `.env.sharefast-bridge.example`. إنشاء الأسرار وتخزينها يتم خارج Git؛ لا تستخدم متغيرات NEXT_PUBLIC.

في شير فاست:
- حساب تاجر الحبوب يجب أن يكون قائمًا وملكيته متحققة إداريًا. ضع مرجعه في `SHAREFAST_EL7BBOB_MERCHANT_REF`؛ لا تعِد استخدام ref قديم من الرابط تلقائيًا ولا ترفع صلاحيات حساب.
- `SHAREFAST_EL7BBOB_ENABLED=true` و`SHAREFAST_EL7BBOB_SECRET` بطول 32 حرفًا على الأقل، في staging فقط.
- `SHAREFAST_EL7BBOB_COMPANY_REF` اختياري؛ إن وُضع، يجب أن توجد علاقة شركة مقبولة بالفعل. بدونها يمكن التشغيل مع مناديب مملوكين للتاجر، ولا يُمنح وصول عشوائي للشركات.

في الحبوب:
- `SHAREFAST_DELIVERY_PROVIDER=sharefast` فقط في staging، مع `SHAREFAST_BRIDGE_URL` أصل HTTPS بلا مسار، ونفس سر التوقيع في `SHAREFAST_BRIDGE_SECRET`.
- عنوان كل فرع يجب أن يكون صحيحًا. التسجيل اليدوي يستخدم `branches.address` أو `SHAREFAST_PICKUP_ADDRESS`؛ لا توجد نقطة استلام وهمية تلقائية.
- Scheduler خارجي يجب أن يستدعي `POST /api/internal/sharefast-outbox` دوريا باستخدام Bearer `SHAREFAST_OUTBOX_DRAIN_TOKEN` مختلف عن سر الربط. لا Scheduler ولا اعتماد على استمرار العملية بعد انتهاء استجابة checkout أُضيف تلقائيًا.
- المنفذ يعالج حتى 10 مهام في الاستدعاء، يخزن fixed error codes فقط، ولا يعيد الطلب للقديم عند timeout. **الرجوع التلقائي للقديم قد يكرر التوصيلة، لذلك ممنوع.**

## قيود مقصودة قبل الإطلاق

- حقول Wasl المالية الحالية INTEGER. عقد v1 يقبل جنيهًا كاملًا فقط، ويحافظ على مبلغ العميل بما فيه رسوم صفر. لا rounding ولا إعادة تسعير صامتة. التعامل مع الكسور المالية يجب حسمه واختباره قبل الإنتاج.
- الدفع النقدي المؤكد مسبقًا، الطلب المغلق قبل أول إرسال، تعارض الهوية، وتعارض الإلغاء تدخل `review` بدل إنشاء توصيلة أو تحصيل ثانٍ بلا تحقق.
- `review` يحتاج شاشة ومشغل لإعادة المعالجة الآمنة؛ **واجهة مراقبة الطابور وإعادة المحاولة الإدارية لم تُضف بعد**.
- مراقبة التحصيل وتسوية النقدية مع المندوب يجب حسمها في الشاشات، ولا تستنتج وصول النقدية للمطعم من `delivered`.
- لم تُضف سياسة أولوية للحبوب ولا نقل حسابات/مناديب/طلبات قديمة. هذه أعمال منفصلة قبل التحويل.

استعلام مراقبة تجريبي بدون بيانات العميل:

```sql
SELECT order_id,state,remote_ref,remote_status,attempts,last_error,updated_at
FROM el7bbob_sharefast_outbox
ORDER BY created_at DESC;
```

لا تعيد `review` إلى `pending` قبل تحديد السبب والتأكد من المهمة البعيدة. لا تغير payload بعد أول إرسال.

## بوابات إلزامية قبل التحويل

- [ ] تحقق أين تنشر النسختان وهل قواعد البيانات منفصلة. لا تشغيلهما على قاعدة مشتركة بالصدفة.
- [ ] Backup بعملية استرجاع مجربة، وحصر الطلبات المفتوحة والحسابات والمناديب في سوبر إكس.
- [ ] استكمال شاشات الحالة والمندوب ومراقبة أخطاء الربط وإعادة المحاولة، مع الحفاظ على كل مسارات الطلب الحالية.
- [ ] حسم الكسور المالية، الدفع النقدي المؤكد مسبقًا، التحصيل، أولويات المطعم، وحالات رفض العميل وعدم الرد.
- [ ] Full lint + typecheck + build + الاختبارات القائمة للريبوين بإصداراتهما المقفلة.
- [ ] اختبار كل شاشة فعليًا: checkout، كاشير المالك باللمس والنموذج، POS، المطبخ، الدليفري، الفواتير، الحسابات، الإدارة؛ كاش وإنستاباي، مخزون، إلغاء، timeout، تكرار الضغط.
- [ ] اختبار PostgreSQL حقيقي بالتزامن وScheduler في staging؛ PGlite محلي لا يثبت سلامة النشر الحي وحده.
- [ ] وقت تحويل محدد: الطلبات الجديدة في نظام واحد فقط. القديمة تُستكمل في القديم أو تُنقل بخطة موثقة؛ لا إعادة إرسال آلي لها.

## الرجوع

قبل أي تفعيل تجريبي/إنتاجي، الرجوع هو إغلاق PR أو الرجوع للكوميت السابق؛ لم يتغير main في مرحلة التجهيز.

بعد وجود مهام مرسلة أو ذات acknowledgement مفقود، **لا تقلب provider إلى القديم مباشرة**. أوقف قبول مهام جديدة في إجراء تشغيلي مدروس، وطابق outbox مع شير فاست، وأكمل/ألغِ المهام الجارية في النظام المسؤول عنها. تغيير provider يوقف drain الحالي؛ لذلك يجب إكمال أو تسليم مسؤولية كل مهمة قبل الرجوع. لا تحذف جداول الربط أو tombstones.

## الاختبارات التي نفذت في بيئة مستقلة

- 40 اختبار Vitest/PGlite: outbox 17، idempotency/ownership/cancellation 13، HTTP authentication 8، ومخطط Wasl الفعلي 2.
- 11 فحص protocol مستقل. في ريبو الحبوب فحصان إضافيان يستعيدان ملفي checkout والتسجيل اليدوي إلى SHA النسخة المراجعة بعد إزالة إضافات الربط فقط، لحماية حسابات/دفع/مخزون القديم من تغيير غير مقصود.
- Focused typecheck لملفات الربط والـroutes باستخدام تعريفات Drizzle الفعلية. هذا **ليس full workspace build أو اختبارًا حيًا للشاشات**.
- جميع بيانات الاختبار محلية وهمية. لا DATABASE_URL إنتاج، ولا توكن مستخدم، ولا أسرار حقيقية.

تشغيل فحص العقد (Node 22.6+ مع دعم strip-types، وNode 24 في بيئة المراجعة):

```bash
node --experimental-strip-types --test apps/web/tests/sharefast-protocol.check.mjs
```

في الحبوب:

```bash
node --experimental-strip-types --test apps/web/tests/sharefast-legacy-diff.check.mjs
```

اختبارات شير فاست الجديدة تدخل runner القائم (`pnpm --filter @el7bboB/web test`). اختبارات outbox في الحبوب استخدمت harness مستقل بـVitest 5.0.3 وPGlite؛ لم تُغيّر package.json أو lockfile ولا تعتبر أنها أُضيفت تلقائيًا إلى CI. شغّلها من harness مؤقت خارج الريبو يوفر الحزم، أو أضف أدوات الاختبار والـlockfile في PR منفصل قبل الدمج.

## مرحلة التجهيز والجاهزية — مسودة غير مفعّلة

قرار المالك: الإرسال تلقائي فور حفظ طلب التوصيل، بما فيه إنستاباي غير المؤكد. لا تأكيد دفع تلقائي ولا تحويل وسيلة الدفع لكاش. في وضع sharefast فقط، يدخل طلب الأكل `queued` مع بقاء عملية إنستاباي `awaiting_confirmation` ليظهر للمطبخ. الكاشير يستطيع تأكيد التحويل بعد بدء التجهيز؛ صلاحية تأكيد الدفع لا تُمنح للمطبخ. تسليم طلب إنستاباي غير المؤكد لا يتجاوز فحص الدفع القائم.

- تقدير اختياري من أصناف الطلب وكمياتها وإضافاتها، حسب محطات التحضير والدفعات، مع وقت تعبئة وهامش انتظار قابلين للضبط. الأصناف غير المضبوطة تعرض «الوقت لم يُحدد»؛ لا افتراض 15 دقيقة للجميع. موعد الجاهزية مطلق مبني على وقت تسجيل طلب الأكل ويُحفظ في payload حتى لا يعاد العدّاد مع retry.
- في هذه المرحلة هامش الانتظار إعداد ثابت؛ قراءة ضغط المطبخ الحي وتعديل التقدير أثناء التحضير لم تنفذا بعد. تغيير قواعد الأصناف لا يغير تقدير طلب تم تسجيله.
- انتقال المطبخ إلى ready يحفظ علامة إرسال داخل نفس transaction لتغيير الحالة. الـdrain يرسل حدث ready إلى endpoint مستقل بتوقيع HMAC. الحدث يُحفظ مرة واحدة لكل أوردر، ويحتفظ بنفس المعرف والوقت عند إعادة الإرسال. إلغاء الطلب يمنع حدث جاهزية جديد. وقت الحدث هو وقت استلام شير للإشارة وليس ادعاء وقت المطبخ الدقيق.
- واجهة المندوب تعرض التقدير أو الجاهزية للطلبات المسندة له فقط حسب صلاحيات السيرفر؛ لا قبول refs من العميل كإذن وصول. مرور موعد التقدير لا يساوي جاهزية فعلية.
- تنبيه داخل التطبيق مع إشعار متصفح اختياري بعد ضغط المندوب تفعيل التنبيهات. يجلب الحالة كل 15 ثانية أثناء تشغيل التطبيق مع الاعتماد كذلك على سرعة الـscheduler؛ يمنع تكرار الإشعار على نفس الجهاز/الحساب عادةً بمعرف الحدث المخزن محليًا. حذف تخزين المتصفح أو استخدام جهاز آخر قد يعيد التنبيه؛ لا ادعاء exactly-once للإشعار على كل الأجهزة.
- **ليس Web Push في الخلفية.** التطبيق المقفول أو جهاز بلا اتصال لا يُضمن وصول تنبيه له. يلزم لاحقًا push subscription مرتبط بالحساب، مفاتيح VAPID في مخزن أسرار، عامل إرسال دائم بإعادة محاولة وتنظيف الاشتراكات غير الصالحة، مستقبل push، واختبار موبايل حقيقي. service worker يحافظ على عدم تخزين APIs/صفحات الحساب، ويضيف فتح لوحة الحساب عند الضغط على التنبيه فقط.

### إعداد تقديرات الأصناف في الحبوب (staging فقط)

`SHAREFAST_PREPARATION_RULES_JSON` اختياري وسيرفر فقط. يحتوي `packingMinutes` و`queueMinutes` و`items` المفهرسة بالـmenuItemId الفعلي (يشمل الإضافات). كل صنف له `station` و`minutesPerBatch` و`batchSize`. الأرقام أوقات تشغيل فعلية يعتمدها المالك؛ لا توجد أرقام منتجات إنتاجية مفترضة في الكود. القيم بين 0 و180 دقيقة، والمدة الإجمالية القصوى 180 دقيقة؛ القيمة غير المعروفة لا تُقرَّب ولا تُختلق. الأصناف الجاهزة للتعبئة يمكن أن يكون وقت تحضيرها صفرًا مع حساب التعبئة.

### بوابات ما زالت تمنع الإطلاق

- مزامنة حقيقة الدفع/المبلغ المطلوب تحصيله للمندوب، وبوابة تحقق قبل التحصيل تمنع الجمع بين تحويل مؤكد وتحصيل نقدي. هذه المرحلة لا تنفذ تسوية أموال المندوب.
- تسعيرة مناطق شير المعتمدة قبل تأكيد طلب الأكل، وإلغاء fallback المناطق غير المعروفة، وسياسة الحساب الرئيسي/الفروع والإعفاء والأولوية.
- ربط الحجوزات المستقلة من أزرار الشاشات القديمة، واجهات مراجعة الربط، تقدير ضغط المطبخ الحي وتحديث ETA، Push الخلفية.
- اختبارات تصرفات شاشات المطبخ والكاشير والصلاحيات فعليًا، PostgreSQL staging، نشر المفاتيح والـscheduler وفصل قواعد البيانات وbackup/restore. لا full build أو E2E أو اختبار تسليم حي نفذ في هذه المرحلة.

### نتيجة المراجعة المحلية لهذه المرحلة

68 اختبار Vitest/PGlite نجح (يشمل السابق): outbox 24، bridge 17، مخطط Wasl الفعلي 2، route القديم 8، تقدير التجهيز 6، readiness route 5، صلاحيات قراءة المندوب 6. و11 فحص عقد و4 حراس source-diff لcheckout/manual وكارت الأوردر/شاشة المطبخ. Focused semantic typecheck لملفات النقل والـreadiness endpoint، وفحص syntax لـ23 ملف TS/TSX معدل وservice worker. اختبارات قراءة المندوب تستخدم mock لآلية نطاق الطلبات القائمة؛ ليس اختبارًا حيًا لصلاحيات قاعدة الإنتاج. تنبيه المتصفح والصلاحيات والمطبخ تحتاج browser/E2E وموبايل، وfull workspace lint/build لم ينفذ.

## لوحات الإعدادات والتقديرات التلقائية — بإذن المالك، مسودة

المالك طلب عدم الانتظار لتحديد أوقات كل صنف، واستخدام تقديرات ابتدائية قابلة للتعديل لاحقًا. هذا يحل محل شرط «لا تقدير بدون إدخال وقت كل صنف» للأصناف المعروفة في كتالوج المطعم فقط؛ الأصناف/الإضافات غير الموجودة في الكتالوج تظل بلا تقدير.

### الحبوب: `/staff/admin/preparation`

- صفحة جديدة في قائمة الإدارة، محمية بـrequireAdmin في القراءة وفي server action؛ لم تُمنح صلاحيات جديدة للكاشير أو المطبخ.
- افتراضات البداية: تعبئة 2 دقيقة وهامش انتظار ثابت 3 دقائق. تقديرات دفعة التحضير حسب التصنيف/اسم الصنف: مشروب جاهز 0، إضافة بسيطة 1، تجميع أساسي 3، ميكس 5، مقليات 6، بيض 7، بوكس 8، لحوم سريعة/شواية 10، طبق 12 دقيقة. أحجام الدفعات تقديرية كذلك. **هذه افتراضات تشغيل لا أوقات مقاسة**، وقد تختلف حسب حالة تجهيز الصنف فعليًا.
- لوحة تعديل التعبئة/هامش الانتظار، تشغيل/إيقاف التقدير التلقائي، وتعديل محطة ووقت وحجم دفعة كل صنف. غير المعدل والأصناف الجديدة يرثون التقدير التلقائي؛ التعديل الخاص للصنف له الأولوية. نفس محطة التحضير تعمل بالتتابع والمحطات المختلفة بالتوازي.
- حفظ في جداول منفصلة بإصدار ومحرر وسجل تغييرات، optimistic concurrency لمنع الكتابة فوق تعديل أحدث، ورسالة نجاح/خطأ واضحة. لا تغيير لأسعار أصناف الأكل أو المخزون.
- الطلب يحفظ التقدير مرة واحدة من وقت تسجيله؛ إعادة enqueue بعد تعديل الإعدادات/كتالوج الأصناف لا تعيد حساب التقدير القديم. تنبيه الجاهزية يظل من ready الفعلي، وليس افتراضات الزمن.
- إعدادات dashboard المحفوظة تتقدم على env القديم؛ قبل أول حفظ فقط يمكن لـSHAREFAST_PREPARATION_RULES_JSON توفير قواعد قديمة صريحة. الافتراضي من dashboard تلقائي مع تصريح المالك.
- هامش الانتظار في هذه المرحلة ثابت؛ قراءة ضغط المطبخ الحي وتحديث ETA أثناء التجهيز لم يُنفذا. لا يدّعي التقدير ضمان موعد الاستلام.

### شير: `/wasl/delivery-pricing`

- صفحة إعداد معادلة ومراجعة الأسعار، محمية بحساب **أدمن المنصة**. حساب الحبوب merchant لا يُرقّى ولا يمكنه تعديل أسعار المنصة. رابطها يظهر للأدمن فقط.
- افتراضات البداية تطابق معاملات معادلة شير الحالية: أساس 15 جنيه، 2.5 جنيه/كم، حد أدنى 25، معامل طريق 1.3، تقريب 5 جنيه. يمكن تعديل المعادلة ومعاينة منطقة استلام مختلفة وإضافة سعر ثابت لكل زوج منطقة استلام/تسليم؛ لا ينتشر سعر الوجهة نفسه بالخطأ لكل الفروع/المدن.
- يحفظ تعديل الأسعار في جداول إعدادات وإصدارات/سجل محرر، ويرفض الحفظ بإصدار قديم. واجهة تعرض التعديلات غير المحفوظة وتمنع تغيير منطقة معاينة الاستلام قبل الحفظ.
- **مسودة ومعاينة فقط**: جدول الإعدادات الجديد لم يُوصَّل بعد بـcheckout الحبوب أو generic order APIs. حفظه لا يغير أي طلب حالي أو جديد حتى استكمال تكامل quote واعتماد لقطة التسعير قبل التأكيد. لا نفترض أن حفظ الإعدادات فعّل التسعيرة.
- المعاينة ترفض المناطق غير المسجلة، لكن fallback القديم في الـAPI العام لم يتغير بعد. القائمة مناطق عامة من الكود الحالي لا سجل أحياء المنصورة؛ التغطية وإحداثيات الاستلام/المناطق تحتاج تحقق قبل إطلاق أسعار فعلية.
- لا تعديل في أجر المندوب أو الاشتراكات/الإعفاء/الأولوية؛ هذه سياسات منفصلة لم تفعّل.

## النطاقات التي طلبها المالك — تقديرات ابتدائية لا ضمانات

- أسعار لوحة شير لا تزال draft/preview غير متصلة بإنشاء الطلبات؛ لا حذف للقديم أو تفعيل provider من تعديل حدود الأسعار/الوقت.

## تسعيرة شير قبل التأكيد — تكامل مسودة، غير مفعل في الإنتاج

هذه المرحلة تستكمل شرط quote في checkout الحبوب والأوردر اليدوي فقط، وتحل محل ملاحظات «الأسعار معاينة فقط» أعلاه لهذين المسارين. الـAPI العام لشير وطلبات المندوب المستقلة من روابط الشاشات القديمة ما زالت خارج هذا التكامل.

- الحبوب يطلب عرض سعر موقّع من شير بعد اختيار المنطقة؛ يعرض سعر شير في الإجمالي ويمنع التأكيد إذا لم يصل سعر صالح. حقول التحويل عبر InstaPay/QR لا تظهر قبل وجود السعر. العميل يرسل quote ID فقط، وليس مبلغ التوصيل المعتمد.
- عند الحفظ، سيرفر الحبوب يقرأ نفس العرض الموقّع ويطابق الفرع/المنطقة ويثبت رسم التوصيل مرة واحدة في الطلب ومبلغ الدفع وoutbox. لا يضاف رسم ثان ولا يؤكد الدفع تلقائيًا. مثال اختبار محلي: منتجات 100 + توصيل 15 = طلب شير بإجمالي 115 ورسم 15.
- شير يحفظ السعر/إصدار الإعدادات/منطقتي الاستلام والتسليم في `sharefast_el7bbob_quotes`، صالح 10 دقائق. تعديل التسعيرة لا يغير العرض السابق قبل انتهاء صلاحيته، ولا يغير الطلب المسجل. `acceptedAt` من سيرفر الحبوب، لا المتصفح. outbox المتأخر بعد انتهاء العرض يظل صالحًا إذا وقت القبول الأصلي داخل نافذة العرض. يجب مزامنة ساعات السيرفرين واختبار ذلك في staging.
- claim محلي في نفس معاملة حفظ الأكل، وclaim في نفس معاملة إنشاء طلب شير. عرض واحد لا ينشئ فاتورتي أكل أو طلبي مندوب. إعادة طلب العميل بنفس البيانات وquote ID تسترجع رقم الطلب المحلي بعد ضياع الرد؛ اختلاف البيانات يرفض بدل إنشاء طلب آخر. إعادة النقل بنفس payload/ID تسترجع طلب شير نفسه؛ لا fallback تلقائي للقديم عند timeout.
- عقد النقل يدعم quote اختياريًا للتوافق مع النسخة السابقة، لكن endpoint إنشاء الطلب على شير **يشترط quote افتراضيًا** عند تفعيل الربط. `SHAREFAST_EL7BBOB_REQUIRE_QUOTES=false` استثناء انتقال مقصود فقط لو هناك outbox قديم بلا quote يحتاج تصريفًا موثقًا؛ لا يضبط تلقائيًا ولا يجعل checkout يتخطى التسعير. لا تسقط jobs القديمة عند تغيير هذا الخيار.

### التغطية والفرع

تم نسخ 84 اسم منطقة وتسعيرتها الابتدائية من ملف `packages/db/src/delivery-zones.ts` في EL7bboB، blob SHA `5efee4ef50c62479e5611d853cf0cc06a0f64624`، لا من قراءة قاعدة الإنتاج. الأسعار المحلية في هذا المصدر 15/20/25/30، ومناطق أبعد 35/40. لا نضغط المناطق البعيدة داخل سقف 30 ولا ندّعي مسح أسعار السوق. تعديلات قاعدة الحبوب الحية غير مقروءة هنا؛ يجب مطابقة الأسماء والأسعار الحية قبل الإطلاق.

- بيانات المناطق تحولت إلى defaults على شير. أدمن شير يستطيع تحديد سعر خاص للمنصورة→حي بعينه من لوحة التسعير؛ السعر الخاص له الأولوية. الحبوب لم يحصل على صلاحية أدمن المنصة.
- `MAIN` يورث منطقة حساب المطعم المربوط على السيرفر؛ يجب التحقق أنها المنصورة وعنوان الاستلام ميدان مشعل. فرع آخر لا يصدر له quote حتى يسجل في `SHAREFAST_EL7BBOB_BRANCH_ZONES_JSON`، مثل `{"MAIN":"المنصورة"}`. هذا تسجيل لمنطقة التسعير فقط، **ليس سياسة الإعفاء أو الأولوية أو إثبات ملكية الفروع**. إنشاء طلب شير الحالي يورث منطقة حساب المطعم؛ لذلك أي mapping لفرع في مدينة مختلفة يُرفض بـ`branch_binding_requires_review` إلى أن يكتمل ربط فرع فعلي وعنوان/منطقة استلامه؛ لا يُسعّر من مدينة ويُرسل للمندوب على مدينة أخرى.
- اختلاف اسم حي في قاعدة الحبوب الحية يحتاج alias صريح في `SHAREFAST_EL7BBOB_DEST_ZONES_JSON` بعد المراجعة. لا fallback لمسافة 8كم ولا أسعار وهمية لأسماء غير مسجلة. أحياء المنصورة لا تنطبق على استلام في مدينة أخرى. إحداثيات مناطق شير العامة الموجودة لا تزال تحتاج تحقق.

### بوابات قبل تفعيل provider

يبقى `legacy`/disabled في المثال والإنتاج؛ هذه الملفات لا ترفع مفاتيح ولا تغير إعداد Railway. قبل التفعيل: مراجعة rate limiting وميزانية إصدار quotes العامة وحماية الكتابة من الإساءة (ليست منفذة في هذه المرحلة)، تنظيف/احتفاظ بالسجلات وفق سياسة متفق عليها دون حذف المستخدمة ماليًا، clock sync، مطابقة DB الحية/الفرع/العنوان/المناطق، PostgreSQL staging مستقل، اختبار صلاحيات الإدارة والعميل والمندوب، full workspace build/lint وbrowser/mobile/E2E. الأرقام المالية في شير integer؛ أسعار الطعام الكسرية بوابة تشغيل لم تحل هنا ولا يجوز تقريبها سرًا.

تظل مزامنة التحصيل/تسوية InstaPay، standalone delivery من كل الشاشات، Push الخلفية، الإعفاء من الاشتراك والأولوية مع الفروع المستقبلية، واجهات تشغيل outbox/failed jobs والـscheduler، فصل قواعد التطبيقين، backup/restore والتعامل مع الطلبات القديمة شروطًا قائمة قبل التقاعد النهائي لسوبر إكس. لا تمسح التطبيق القديم أو الجداول/البيانات المالية بناءً على نجاح الاختبارات المحلية.

### تحقق محلي لمرحلة quote

119 اختبارًا في harness الربط + 5 اختبارات server action الإدارة = **124 اختبار Vitest مختلفًا**، و16 فحص Node للعقد/source-diff، نجحوا. يشمل ذلك quote إصدار/صلاحية/هوية/فرع/منطقة، ثبات السعر بعد تعديل الإعدادات، توقيع body/query، تكرار الطلب، رفض إعادة استخدام العرض، rollback المحلي والبعيد، قبول outbox متأخر داخل نافذة القبول الأصلية، توافق claim/طلب شير مع DDL الموجود فعليًا على PGlite، وتغطية أسماء الـ84 منطقة. focused server semantic typecheck وفحص syntax لـ48 ملف TS/TSX نجحا؛ نسختا البروتوكول متطابقتان.

## طلب المندوب المستقل من شاشات الحبوب — مسودة غير منشورة

هذه المرحلة تستكمل مسار الطلب المستقل من الأزرار المعروفة في الكاشير والمطبخ والدليفري ومركز تشغيل الفرع (StaffHeader المشترك)، ولوحة طلبات المالك، وتضيف مدخلًا في قائمة الإدارة. لا تستبدل بقية لوحة Super X ولا تعني اكتمال تقاعده.

### المسار والصلاحيات

- الأزرار تفتح `/staff/delivery-requests` مع الفرع الحالي في شاشات الفرع. السيرفر يقرأ جلسة موظف الحبوب ويفرض `requireBranchAccess` على التسعير والقائمة والحفظ والجاهزية والإلغاء والتحديث. الأدمن يختار من الفروع النشطة، وباقي الأدوار مقيدة بفرع الموظف. المطبخ يحتفظ بإمكانية طلب مندوب التي كان يعرضها الزر القديم؛ لا يمنح صلاحيات تحصيل أو إدارة أسعار شير.
- هوية المنشئ وعنوان الاستلام من السيرفر/الفرع النشط، لا حقول العميل. عنوان فرع فارغ يوقف الحفظ؛ لا تخمين عنوان فرع مستقبلي. فرع الاستلام يجب أن يمر أيضًا ببوابة quote/enrollment الحالية.
- حين `provider=legacy` ولا يوجد سجل مستقل، المدخل يعيد التوجيه إلى الرابط القديم كما هو. إذا سبق إنشاء السجل، يبقى ظاهرًا **للقراءة فقط** عند التراجع حتى لو الفرع المختار فارغ، مع اختيار الفروع المسموح بها. لا يخفي طلبات شير السابقة أو يعيد إرسالها للقديم، ولا ينشط الحفظ/النقل/الإلغاء/الجاهزية في وضع legacy. رابط القديم لشحنة جديدة مختلفة فقط مع تحذير من إعادة نفس الشحنة.

### لا فاتورة أكل وهمية

- جدول منفصل `el7bbob_sharefast_deliveries` يحفظ الشحنة والفرع والمنشئ وquote ID وبصمة الإدخال والحالة. لا INSERT/UPDATE/DELETE إلى orders/order_items/payments أو المخزون، ولا تخصيص رقم فاتورة أكل أو FK يفرض إنشاء طلب أكل. الاختبار المحلي شغل السجل والنقل في قاعدة لا تحتوي أي جداول أكل/دفع/مخزون.
- السعر من quote مستقل موقّع قبل الحفظ، وليس مبلغ توصيل من المتصفح. قيمة الشحنة المدخلة + رسم التوصيل تُرسل إجماليًا معلنًا للمندوب. صفر قيمة شحنة يعني توصيل فقط؛ اختيار InstaPay لا يؤكد وصول التحويل. **هذا سجل شحن وليس دفتر تحصيل مالي**، والتسوية المالية ما زالت بوابة إطلاق.
- النموذج يطلب تأكيد أن الشحنة ليس لها طلب مندوب تلقائي بالفعل، ويحتفظ بمعرّف محاولة في sessionStorage فقط (لا بيانات عميل). بعد بدء الإرسال يقفل تعديل المحاولة؛ إعادة المحاولة تستخدم نفس ID ونفس الإدخال وquote لاسترجاع نتيجة الحفظ. بدء شحنة أخرى إجراء صريح بعد مراجعة السجل، يفرغ البيانات ويولد ID جديدًا، ولا يلغي الشحنة السابقة.
- التقدير المستقل إدخال موظف 0–180 دقيقة، ابتدائي 20 دقيقة، وليس حساب أصناف أكل غير موجودة. زر «الشحنة جاهزة فعلًا» هو الجاهزية الفعلية؛ 0 دقيقة أو انتهاء التقدير لا ينشئ ready تلقائيًا. إشعار الجاهزية يستخدم حدث شير الحالي؛ لا يدعي وصول Push في الخلفية أو وصول الإشعار لهاتف المندوب.

### عزل النوع والفرع في شير

- endpoint مستقل POST/GET/PATCH `/api/integrations/el7bbob/deliveries`. الحفظ يقبل عقدًا موقّعًا `requestKind=standalone` و`source=staff_standalone` مع quote إلزامي حتى عند تعطيل شرط quote لتصريف outbox أكل قديم. endpoint الأكل لا يقبل نوع standalone.
- GET/PATCH يطلبان branchCode مع externalOrderId، ويطابقان نوع الربط والفرع والـmerchant المربوط على السيرفر. تصادم أو محاولة استعمال ID لطلب أكل أو فرع آخر **لا يلغي ولا يقرأ الطلب الآخر**. الـtombstone مقيد بالنوع والفرع، ولا يُحيي POST متأخر شحنة ألغيت قبل الإرسال.
- `request_kind` و`branch_code` أعمدة إضافية في جدول links؛ الروابط/الـtombstones القديمة تعامل food افتراضيًا ولا تعاد كتابة بصماتها أو أرقامها أو بياناتها المالية. quotes القديمة أيضًا food؛ quote مستقل لا يستخدم لحفظ فاتورة أكل والعكس. `kind` في wasl_orders يميز «طلب توصيل مستقل» عن «أوردر طعام»؛ أرقام SX الموجودة تبقى مراجع محفوظة ولا تعاد تسميتها جماعيًا.

### النقل والمراجعة والتراجع

- الحفظ المحلي أولًا، والنقل لا يحدث داخل transaction ولا يعتمد على بقاء شاشة المستخدم مفتوحة. العامل المحمي الحالي يصرف 5 طلبات أكل + 5 شحنات مستقلة في كل استدعاء لتقييد زمن العمل؛ يجب ضبط وتقييم تردد scheduler والسعة في staging، فهو **غير موصل بجدولة إنتاج هنا**.
- سجل مستقل بlease خمس دقائق وSKIP LOCKED، retries/backoff وثبات ID، وتحقق هوية الرد، ولا fallback تلقائي إلى القديم. الإلغاء قبل الإرسال يرسل tombstone بدل POST. انتهاء lease يمنع العامل القديم من الكتابة فوق إقرار عامل بديل، وحساب النتائج يميز lostLease. payload/هوية محلية تالفة تذهب review قبل HTTP؛ الأخطاء المحفوظة أكواد ثابتة لا بيانات عميل/مفاتيح.
- الواجهة تعرض آخر 30 سجلًا للفرع، آخر حالة وصلت من شير (لا تتبع حي)، وتفرق بين «محفوظ محليًا/ينتظر الإرسال» وقبول المندوب. بها طلب إلغاء وجاهزية صريحان وتحديث نقل لسجل موجود فقط. إلغاء بعد heading أو تعارض يحتاج مراجعة؛ لا إعادة فتح أو حذف أو retry بالقوة لسجلات review من العميل. ما زالت أدوات معالجة تعارضات التشغيل ومسار الدعم/الأرشفة بحاجة لإكمال.
- لا تنظيف تلقائي للـquotes بمجرد انتهاء عرضها: عرض منتهي وغير claimed على شير قد يكون قبله الحبوب وحفظه في outbox متأخر. سياسة الاحتفاظ يجب أن تراعي ذلك؛ حذف السجل عشوائيًا يكسر ثبات السعر والنقل. لا حذف تلقائي للـtombstones أو الشحنات/الطلبات المالية.

تظل الاختبارات الحية لكل شاشة/دور، full workspace build/lint وUI typecheck، E2E/mوبايل وPostgreSQL staging، rate limiting للquotes العامة، clocks/DB الحية/العناوين، التحصيل/الاشتراكات والأولوية والفروع، Web Push الخلفية، أدوات failed jobs، DB separation وbackup/restore وruntime scheduler والتعامل مع الطلبات القديمة شروطًا قبل التفعيل والحذف. الكود الجديد لا يفعّل provider ولا يدمج PR أو ينشر على Railway.

### تحقق مرحلة الشحن المستقل

141 اختبارًا في harness الربط + 16 اختبار server actions/الإدارة = **157 اختبار Vitest مختلفًا** نجحوا محليًا. و21 فحص Node للعقد/source-diff نجحوا؛ focused semantic typecheck لوحدات السيرفر وفحص syntax لـ59 ملف TS/TSX نجحا، ونسختا البروتوكول متطابقتان. يشمل التحقق lease/concurrency/lost ACK/backoff، من دون جداول أكل/دفع في قاعدة السجل المستقل، والصلاحيات بعزل جلسات mocked، والحفظ/الإلغاء/quote purpose/branch namespace على DDL شير الفعلي داخل PGlite.

حراس source-diff يثبتون أن لوحة المالك أبقت كل handlers الأكل والدفع والإنذارات، وStaffHeader أبقى الاسم والخروج وكل الشاشات، وشاشة الدليفري أبقت فلاترها/حساباتها مع تعديل وصف InstaPay حسب provider. هذه ليست اختبارات تفاعل شاشة أو Next/React runtime، ولا full workspace build/UI typecheck/E2E/موبايل/إنتاج. لم تتغير dependencies/lockfiles في المستودعين، ولم تنفذ طلبات حقيقية أو تحصيل أو نشر أو حذف.

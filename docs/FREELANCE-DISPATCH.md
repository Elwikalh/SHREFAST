# مسار المندوب الحر — عروض وقبول ذري

## ما نفذ
- `/api/wasl/freelance/settings`: إعداد شخصي موثق على الخادم؛ موافقة النشاط على عروض طلباته العادية، أو توفر حساب المندوب لاستقبالها. الافتراضي متوقف. revisions وaudit تمنع الكتابة فوق تعديل جلسة أخرى.
- `/api/wasl/freelance/offers`: مندوب مسجل نشط ومؤهل وفق الاشتراك القائم، متاح وغير مشغول. المحافظة والمنطقة من قاعدة الحساب لا من query أو browser؛ ليست GPS. العروض محدودة بـ30 وبنفس منطقة الاستلام والمحافظة، وليس منطقة التسليم.
- لا عرض لطلب شركة/أسطول أو طلب له مندوب أو اسم مندوب محجوز. موافقة النشاط الصريحة أو وجود رابط طلب الحبوب الموقّع شرط العرض؛ لا وراثة من الاسم أو الهاتف أو تفضيلات واجهة توضيحية غير محفوظة.
- العرض يحتوي اسم النشاط والمنطقتين ورسوم الطلب وتقدير التجهيز/الجاهزية الحقيقية فقط؛ لا هاتف أو اسم العميل أو العنوان الدقيق أو الملاحظات أو مبلغ الأكل.
- أولوية العائلة الموثقة ثم FIFO عند تشغيل سياسة الملكية الموثقة؛ ترتيب فقط، ليس إجبار المندوب على قبول طلب بعينه ولا سحب رحلة مقبولة.
- `/api/wasl/freelance/claim`: الجسم `orderRef` فقط؛ هوية المندوب من الجلسة ومطابقتها بحساب قاعدة البيانات. قفل حساب المندوب ثم الطلب، إعادة التحقق من الأهلية والتوفر والنطاق والموافقة، ثم assignment وledger وaudit في معاملة واحدة.
- retries لنفس المندوب/الطلب تسترجع النتيجة المثبتة دون قبول أو تحصيل جديد، حتى لو توقف استقبال العروض أو تغيرت الأهلية بعد القبول. تغيير الإسناد إلى شخص آخر لا يعيد كشف بياناته للمندوب الأول.
- المساران القديمان `advance` و`company/assign` يستخدمان قفل نفس الشخص، مع ربط aliases الأسطول عبر account_id؛ إسناد نشط باسم فقط بلا هوية يوقف القبول احتياطياً عند تطابق الاسم ولا يمنح صلاحية الاطلاع. تراجع هوية هذه السجلات تشغيلياً بدلاً من تخمينها.
- رسوم الطلب والدفع ومبلغ الأكل والاشتراكات والأجور والصلاحيات لا تتغير. قبول المندوب لا يؤكد InstaPay. بعد القبول تظهر التفاصيل عبر قائمة الطلبات القديمة المقيدة بالهوية؛ المسار الجديد يعيد المرجع والحالة فقط.

## الواجهة
- لوحة شير `/wasl` تضم لوحة «عروض الطلبات المستقلة» للمندوب، ولوحة موافقة الشبكة للنشاط. زر الشبكة يخص العروض الجديدة ولا يلغي مهمة مقبولة أو يستبدل إسناد الشركة.
- عند فقد الرد، تحفظ sessionStorage المرجع فقط لكل حساب، تمنع قبول طلب مختلف وتتيح التحقق من نفس الطلب حتى بعد reload. ليست مخزناً لبيانات العميل أو سر الدخول.
- التحديث كل15 ثانية أثناء فتح التطبيق؛ تشغيل توفر المندوب لا يعني وجود GPS أو حضور حي بعد إغلاق التطبيق. لا يدّعي هذا المسار وجود push خلفية.
- طلبات الحبوب الموقعة تطلب الشبكة تلقائياً عند تشغيل الربط؛ إيقاف موافقة النشاط العامة لا يلغي هذا الطلب الموقّع ولا مهمة مقبولة. الإلغاء له مساره وتحقق tombstone الخاص به.

## التحقق الحالي
نجح lint وtypecheck والبناء الكامل، و214 اختبار Vitest في21 ملفاً و18 فحص source/contract Node. اختبارات التخزين PGlite محلية بمخطط Wasl الحقيقي وجدول حسابات اختبار مصغر؛ اختبارات السباقات معاملات محلية مجدولة وليست إثبات تنافس PostgreSQL/شبكة إنتاج. اختبارات الواجهة بحسابات وواجهات API محاكاة على كمبيوتر وموبايل ما زالت قيد التشغيل عند حفظ هذا الملف؛ سجّل نتيجتها في PR قبل الدمج.

## ما يمنع إعلان اكتمال تحويل الحبوب
- تفعيل إعدادات التشغيل في Railway يحتاج وصولاً للمتغيرات، لا مجرد push GitHub: secret بين الخادمين، عنوان الخدمة، هوية merchant/account الموثقة، provider الحبوب ومفتاح API/سياسة شير، وعامل outbox والجدولة. لا يوضع السر في GitHub أو chat، ولا يستخدم PAT كسر ربط. راجع `.env.sharefast-bridge.example`.
- اختبار staging على PostgreSQL منفصل، كل شاشات الحبوب المطلوبة، quote/order/outbox/claim/ready/delivery/cancel/retry، والتحقق من الربط الفعلي لكل فرع. لا تفترض أن فحص صحة HTTP يثبت سلامة البيانات أو هذا التدفق.
- Web Push خلفية وخدمة إرسال/إعادة محاولات لم تنفذ. الفوترة/التحصيل لا تصبح مكتملة بسبب وجود entitlement subscription policy.
- لا حذف Super X قبل نجاح الاختبار الفعلي وخطة الرجوع؛ لا fallback تلقائي بعد timeout يعيد إنشاء طلب مندوب.

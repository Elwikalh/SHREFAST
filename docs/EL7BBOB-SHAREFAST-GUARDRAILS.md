# إرشادات حماية ربط الحبوب بشير — اقرأ قبل تعديل المشروع

هذا الملف أضيف بطلب مالك المشروع لتنسيق العمل بين المحادثات والمطورين. الهدف الحفاظ على العمل المنجز ومنع تكرار الطلبات أو كشف بيانات العملاء أو كسر تشغيل الحبوب. ليس منعًا لتحسين الواجهة أو إصلاح علة: يمكن تعديل التنفيذ مع الحفاظ على الضمانات أدناه، واختبار التغيير وتوثيق أي تغيير مقصود في العقود.

## 1. ابدأ من النسخة الصحيحة

- الريبو: `Elwikalh/SHREFAST`؛ الريبو المقابل للمطعم: `Elwikalh/EL7bboB`.
- مراحل الربط مدمجة في `main` عبر [PR3](https://github.com/Elwikalh/SHREFAST/pull/3)، ثم مسار المندوب الحر عبر [PR4](https://github.com/Elwikalh/SHREFAST/pull/4).
- نقطة تنفيذ موثقة قبل إضافة هذا الملف: merge commit `0f1a9043a41fafd51b1e4b2d816909f62db5ce2f`، ورأس تنفيذ مرحلة المندوب `792a0543735c991337dec277b26948d3eaf1398f`. هذه مراجع تاريخية، وليست أمرًا بالرجوع إليها أو الكتابة فوق أحدث شغل.
- اسحب أحدث `main` قبل التعديل؛ افحص الفروع والتغييرات الحالية. لا تنفذ reset/force-push أو تعيد ملفات من نسخة قديمة فوق عمل محادثة أخرى.
- بعض ملفات التسليم القديمة تقول إن الكود مسودة غير مدمجة؛ تلك حالة سابقة. الكود نُشر، لكن نشره لا يعني أن الربط التشغيلي كله فُعّل. لا تغير الإعدادات السرية اعتمادًا على وصف قديم.

## 2. ما نُفذ في شير

### أ. واجهة استقبال الحبوب المؤمّنة
- API للطلبات الغذائية في `/api/integrations/el7bbob/orders`، ومسار منفصل لطلبات التوصيل المستقلة في `/api/integrations/el7bbob/deliveries`، وتسعيرة قبل التأكيد عبر مسارات quote الخاصة بالربط.
- عقد v1 مشترك مع الحبوب: توقيع HMAC يربط method/path/query/body، صلاحية زمنية محدودة، حد لحجم الطلب، وهوية المطعم من إعدادات الخادم لا من جسم الطلب.
- منع إنشاء نفس المهمة مرتين؛ إعادة نفس الطلب آمنة، وتغيير المحتوى تحت نفس الهوية يُرفض. tombstones تمنع إنشاء مهمة متأخرة بعد الإلغاء/فقد الرد.
- عزل food عن standalone وعن الفروع. لا تسمح لمسار مستقل بقراءة/إلغاء طلب أكل أو طلب فرع آخر بمجرد معرفة UUID.

### ب. التسعير والتجهيز والجاهزية
- إعدادات تسعير محفوظة بمراجعات وتدقيق؛ quote مجمد لمدة قبول محدودة، له purpose food/standalone، ويُستهلك مرة واحدة داخل معاملة إنشاء التوصيلة.
- acceptedAt مصدره خادم الحبوب، لا المتصفح. وصول outbox متأخر لا يعيد تسعير quote قُبل داخل نافذته الصحيحة.
- 84 منطقة منصورة من المصدر المراجع؛ المحلي تقديريًا 15–30 جنيه، ومناطق خارجية موجودة 35–40. ليست مسحًا للسوق أو تحققًا من كل override في قاعدة الإنتاج. لا تقص المناطق الخارجية إلى30.
- تقدير التجهيز لا يعني الجاهزية؛ الإعلان الفعلي من المطبخ وحده يولد event جاهزية محفوظًا وقابلًا لإعادة المحاولة دون تكرار.
- التنبيه الحالي أثناء فتح التطبيق، وليس Web Push مضمونًا بعد إغلاقه.

### ج. سياسة الحبوب والفروع
- تحقق الحساب الرئيسي بهوية merchant/account على الخادم، والفروع المنفصلة بتوثيق ملكية من أدمن المنصة ومراجعات/audit. لا وراثة بالاسم أو الهاتف.
- الإعفاء يخص اشتراك التطبيق فقط؛ لا يلغي رسوم التوصيل أو أجرة المندوب أو اشتراك المندوب ولا يختلق paid status.
- السياسة entitlement وليست منظومة فوترة/تحصيل مكتملة. لا تحولها إلى paid=true أو تسوية ديون قديمة.
- أولوية للعائلة الموثقة في ترتيب الطلبات المنتظرة، ثم FIFO. ليست إلغاء مهمة مقبولة أو إجبار المندوب على قبول مطعم معين أو ضمان توفره.

### د. عروض المندوب الحر وقبوله
- `/api/wasl/freelance/settings`: موافقة صريحة للنشاط على إتاحة طلباته، أو توفر المندوب للشبكة، بهوية الجلسة ومراجعة revision وتدقيق. الافتراضي متوقف.
- `/api/wasl/freelance/offers`: للمندوب النشط المؤهل وفق الاشتراك والنطاق المحفوظ في قاعدة الحساب، وليس query/client GPS. نفس محافظة ومنطقة الاستلام، حد30 عرضًا.
- موافقة النشاط الصريحة أو وجود رابط طلب الحبوب الموقّع شرط العرض. لا تعتمد على إعدادات واجهة توضيحية غير محفوظة.
- لا تعرض للشبكة طلب شركة/أسطول أو طلبًا له courier_ref أو اسم مندوب محجوز.
- العروض منقحة: لا اسم/هاتف العميل، ولا عنوان دقيق، ولا ملاحظات أو مبلغ الأكل. يسمح باسم النشاط والمنطقتين ورسوم الطلب والتقدير/الجاهزية.
- `/api/wasl/freelance/claim`: الجسم orderRef فقط. تحقق هوية المندوب من الجلسة/قاعدة البيانات، وقفل الشخص والطلب، والتحقق مجددًا من الأهلية والتوفر والنطاق والموافقة، ثم assignment وclaim ledger وaudit في معاملة واحدة.
- إعادة نفس المحاولة تسترجع النتيجة المثبتة، حتى لو توقف استقبال العروض أو تغيرت الأهلية لاحقًا. إذا تغير الإسناد لشخص آخر، لا تكشف بياناته للمندوب الأول.
- `advance` و`company/assign` يستخدمان قفل الشخص المشترك مع aliases الأسطول عبر account_id. لا تقبل مهمتين لنفس الشخص أو مندوبين لنفس المهمة.
- إسناد قديم باسم فقط يوقف قبولًا إضافيًا احتياطيًا عند التطابق، لكنه لا يمنح صلاحية رؤية بيانات الطلب. لا تستخدم الأسماء كإثبات ملكية؛ السجلات المبهمة تحتاج مراجعة.
- الواجهة تحفظ المرجع فقط في sessionStorage لكل حساب عند فقد الرد، وتمنع محاولة طلب مختلف إلى أن تُحسم النتيجة. لا تحفظ أسرار الجلسة أو بيانات العميل هناك.

## 3. ثوابت لا يجوز كسرها

1. **الهوية من الخادم:** تغيير role/ref/accountId في URL/body/localStorage لا يمنح صلاحيات. لا تفتح قائمة جميع الطلبات للمندوب بحجة إصلاح العروض.
2. **الإسناد الذري:** لا تستبدل الأقفال/المعاملة بـread ثم write منفصلين؛ استخدم نفس قفل الشخص في كل مسار إسناد جديد، بما فيه aliases الأسطول.
3. **الأمان عند التكرار:** لا تحذف uniqueness/claim ledger/tombstones/quote claims/leases أو تتجاوز فحص fingerprint لتسهيل retry.
4. **عدم ازدواج التوصيل:** لا fallback تلقائي إلى Super X بعد timeout؛ الخادم الآخر قد يكون حفظ المهمة رغم فقد الرد.
5. **الحفاظ على المال:** لا تغيّر fee/order_total/pay في قبول المندوب؛ لا تحصّل رسومًا مرتين، ولا تحول InstaPay غير المؤكد إلى مدفوع أو كاش تلقائيًا. طلب المندوب لا يشترط تأكيد الدفع لكنه لا يؤكد الدفع.
6. **جاهزية حقيقية:** انتهاء ETA ليس إعلان جاهزية، ولا يوجد auto-ready من الساعة. الطلبات الكبيرة قد تحتاج وقتًا أكثر من التقدير الابتدائي10–20 دقيقة.
7. **حماية الفروع:** لا تعمم تسعير/عنوان فرع على مدينة أخرى، ولا تقبل branchCode من العميل دون تحقق وصلاحية. الفروع الجديدة تحتاج ربطًا ماديًا صحيحًا.
8. **الحفاظ على الشغل القديم:** لا حذف Super X أو بياناته أو نقل مسؤولية طلباته الجارية قبل إثبات البديل وخطة الرجوع. ما يخص الحبوب يحتاج مراجعة الريبو المقابل، وليس تعديل شير وحده.
9. **لا صلاحيات ضمنية:** حساب الحبوب الذي جهزته هذه الجلسة حساب مطعم، لا أدمن منصة. لا ترقّه بسبب الاسم/رقم الهاتف أو لفتح صفحة التسعير. إنشاء/استعادة أدمن يتطلب مشغّلًا موثوقًا ووصول DB بعد تحقق، وليس تسجيل admin عامًا أو بيانات افتراضية في الكود.
10. **لا أسرار في GitHub:** لا تنشر كلمة مرور/PAT/سر HMAC/رابط DB/توكن العامل. لا تستخدم GitHub PAT كسر ربط بين التطبيقين. لا تعطل origin/auth checks أو bootstrap إنتاج لتجاوز اختبار فاشل.

### جداول الربط الجديدة التي يجب الحفاظ على ضماناتها
- `sharefast_el7bbob_links` و`sharefast_el7bbob_quotes` و`sharefast_preparation_events`.
- `sharefast_owned_restaurant_branches` و`sharefast_owned_restaurant_audit`.
- `sharefast_freelance_merchants` و`sharefast_freelance_availability` و`sharefast_freelance_claims` و`sharefast_freelance_audit`.
- في الحبوب: outbox دائم وledger طلبات مستقلة وlocal quote claims؛ لا تغيّر معناها أو تعيد إنشاء بياناتها من واجهة شير.

أي تغيير عقد/أسماء أعمدة/حالات/معنى quote يحتاج ترحيلًا متوافقًا وتنسيقًا مع الريبوين. لا تسقط جداول أو uniqueness على الإنتاج كتجربة.

## 5. ما لم ينتهِ — لا تخلط نشر الكود بالتفعيل

- لم تضبط هذه الجلسة أسرار/متغيرات التشغيل في Railway أو عامل outbox/الجدولة. الطابور الدائم يحتاج عاملًا يرسل ويعيد المحاولة؛ نشر GitHub لا ينشئ هذا الإعداد تلقائيًا.
- أمثلة إعدادات الخادم في `.env.sharefast-bridge.example`. في الحبوب: provider وbridge URL/secret وdrain token؛ في شير: enabled وsecret وmerchant/account binding وسياسة الملكية والربط الجغرافي للفروع. لا تفترض قيم production من الأمثلة أو من اسم النشاط.
- لم تختبر هذه الجلسة الطلب الحقيقي الذي قال المالك إنه أنشأه على الحبوب؛ لا تقل إنه وصل لشير من غير قراءة معتمدة وتتبع رقمه. لا تطلب مندوبًا ثانيًا لنفس الشحنة قبل التحقق من الموجود.
- لم ينفذ Web Push الخلفية وخدمة إرسال/إعادة محاولاته. المؤكد الآن هو التحديث/تنبيه الجاهزية أثناء فتح التطبيق والاتصال فقط.
- سياسة إعفاء الاشتراك ليست فاتورة أو نظام تحصيل/تجديد مكتملًا، ولا تغيّر أجرة المندوب.
- يلزم staging منفصل على PostgreSQL وتجربة دورة checkout/quote/save/outbox/offer/claim/ready/delivery/cancel/retry، وكل شاشات الحبوب المطلوبة والفروع، قبل التحويل الكامل وحذف القديم.
- الملاحظات التاريخية عن admin لا تثبت أنه غير موجود الآن؛ لم تنشئ هذه الجلسة أدمن، ولم تفحص قائمة حسابات production. راجع الواقع عبر وصول موثوق قبل إنشاء حساب أو إعادة تعيين كلمة مرور.

### دليل النشر المتاح وحدوده
رصدنا بعد نشر المراحل صفحات التسعير والسياسة الجديدة بـHTTP200، ومساري freelance/settings وfreelance/offers من404 إلى401 بدون جلسة، مع health200. هذا دليل ظهور المسارات وحماية الدخول فقط؛ ليس دليل نجاح طلب إنتاج، أو سلامة كل البيانات والشاشات، أو تفعيل flags. لا تعتبر opt-in/availability المحفوظة وعدًا بوجود GPS أو مندوب متصل بعد إغلاق التطبيق.

## 6. اختبارات يجب إعادة تشغيلها قبل الدمج

من جذر الريبو، باستخدام package manager والـlockfile الحاليين:

```sh
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
node --test apps/web/tests/*.check.mjs
pnpm --filter @el7bboB/web... build
pnpm --filter @el7bboB/web exec playwright test --workers 2
```

اختبارات Playwright تحتاج المتصفح المحلي المناسب؛ يمكن ضبط `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` عند الحاجة. استخدم fixture/local DB، لا بيانات إنتاج أو courier حقيقي للتجربة. إعداد UI test المعزول يعمل في development فقط؛ لا تتجاوز instrumentation إنتاج لإخفاء نقص DB.

آخر نتيجة مرجعية:215 Vitest في21 ملفًا،18 Node guards،lint/typecheck/build ناجحة.76 تنفيذ Playwright =38 سيناريو على كمبيوتر وموبايل؛ ثم10 إعادة تحقق لمسار المندوب بعد إصلاح keys، وليست86 اختبارات متميزة. PGlite بمخطط Wasl الحقيقي وجدول auth مصغر، وواجهات API/session محاكاة لا تثبت تنافس PostgreSQL أو دورة production كاملة.

اختبار الخادم المحلي يغطي receiver HTTP موقّعًا ثم استهلاك quote وعرض/قبول المندوب وإعلان جاهزية فعلي ومسار pickup/heading/arrived/delivered دون تغيير InstaPay أو fee/total. حافظ على اختبارات فقد الرد، رفض هوية أخرى، revocation، aliases الأسطول، rollback عند فشل ledger، وخصوصية العميل قبل وبعد القبول.

عند تعديل الواجهة، أعد أيضًا اختبارات تسجيل الدخول/التسجيل/الطلب السريع والأدوار والموبايل، لا تختبر الصفحة الجديدة وحدها. عند تعارض source guard مع تحسين مشروع، راجع التغيير المقصود ووثقه بدلاً من حذف الاختبار أو تعطيل قواعد الفحص عمومًا.

## 7. طريقة تنسيق العمل مع محادثة أخرى

- اقرأ هذا الملف والأدلة المشار إليها قبل أي تعديل يمس الربط.
- اعمل على فرع مخصص للتغيير؛ راجع أحدث main وdiff قبل push/merge، ولا تنسخ ملفًا كبيرًا من snapshot قديم.
- قبل تغيير API/schema مشترك: اذكر التأثير على الريبو الآخر، توافق الطلبات القديمة، migration وخطة الرجوع، والاختبارات التي تثبت عدم تكرار الطلب/الإسناد.
- لا تعدّل أسرار/flags أو تنفذ reset/migration/delete على production كجزء جانبي من تحسين التصميم.
- بعد أي تغيير مقصود لهذه الضمانات: حدّث هذا الملف والدليل التفصيلي وPR بنتائج الفحص وحالة النشر/التفعيل الفعلية. لا تكتب «تم بالكامل» بينما ما زالت هناك بوابات تشغيل.
